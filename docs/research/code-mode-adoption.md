# Code Mode as Staf's primary tool interface

Checked 2026-11-03. This is research, not a specification, accepted decision, or authorization to build. It extends [the first note](code-mode.md), especially its treatment of local runtimes and approvals. The source versions below are snapshots, not claims about later releases. No generated code, runtime, provider, or prototype was run for this research.

## Recommendation

Treat a single model-facing code tool as a **defensible target to test**, not as the default to adopt now. It fits Staf's service-owned dispatch and simple chat direction: a program can combine capabilities while the service owns authority and records actual actions. It may also make a growing capability catalog easier for a model to compose. Neither streamlined prompts nor successful function-call formatting proves that Staf's chosen models can reliably write correct programs, or that the extra runtime earns its cost for simple requests.

Design the experiment around one service-owned capability contract and one policy path. If it passes, make code the normal model-facing path for supported capabilities and retire redundant model-facing direct declarations. Retain a direct entry point only for a demonstrated provider or content-type constraint, with a named owner and a removal or review condition. Direct service operations for clients and deterministic product controls remain available; they are not a second model tool architecture. If the experiment fails, retain direct model tools without building a permanent parallel executor.

This respects [Staf's dispatch decision](../decisions.md#keep-conversation-state-and-tool-dispatch-in-staf), its [simple-chat decision](../decisions.md#simple-chat-before-background-task-workflows), and [local deployment boundary](../adr/0001-shared-instance-web-first.md). It does not reopen them. The source audit below distinguishes existing integration points from proposed behavior.

## Staf source audit and proposed integration

Static source at `9eb427232a44c3bc947caf79e0ad4cbd31fa8ea3` supports a narrower migration than replacing the shared runtime:

- [Direct Responses](../../src/codex-direct.ts) maps supplied function declarations into provider requests. [OpenRouter streaming](../../src/openrouter-stream.ts) and the [compatible providers](../../src/providers.ts) also accept supplied tools. A function with a code-string argument fits these existing transport shapes. This is source evidence for a protocol path, not a successful model or authentication test. The deterministic Demo provider would need its own code-mode fixture behavior.
- [runTurn](../../src/runtime.ts) currently constructs direct tool declarations and dispatches their names. [ToolDefinition and Message](../../src/types.ts) describe simple input schemas and string tool results. A code tool needs a capability bridge, structured result contracts, instructions for the generated code, and child-call limits in addition to the existing provider-step limit. Start the experiment with text and JSON-safe data. Add media support when a concrete capability requires it.
- [ActionBroker](../../src/action-broker.ts) already checks policy before approval and again before dispatch. Web, search, and shell callbacks in the [service](../../src/instance-service.ts) use it. Clock authorization and skill availability have separate runtime checks. A new bridge must preserve those checks and their current scope, rather than expose arbitrary methods from the instance object. Owner-only product operations do not become model capabilities merely because they exist in the service.
- The [command event store](../../src/instance.ts) and [chat work view](../../web/components/ChatWorkItems.vue) already retain and show tool progress. They need explicit parent-execution and child-action correlation for compound scripts. One outer success or failure would not describe the work that actually happened.
- Failed main-chat turns in `runTurn` roll back conversation messages. They cannot roll back external effects. The [action journal](../../src/action-journal.ts) records action outcomes and safe summaries, not a complete interpreter checkpoint. It must not be treated as an existing program-replay engine.

**Initial design recommendation:** use a disposable execution context per outer call, support approvals through supervised host-call waits, and retain Staf's interrupted-on-restart behavior. Keeping a worker alive during a wait requires a bounded number of pending executions and an explicit approval expiry. Restart ends the invocation and preserves action outcomes. This tests Code Mode without first adopting durable script replay or persistent interpreter sessions. The existing [scratch command sandbox](../../src/shell-sandbox.ts) is a separate capability and does not provide the proposed callback bridge.

## What Cloudflare actually supplies

At [Cloudflare Agents commit `455b47e`](https://github.com/cloudflare/agents/blob/455b47ec93f99f306f644ac06bc8b72b0627c1fc/packages/codemode/package.json), `@cloudflare/codemode` identifies itself as version 0.5.6 and MIT licensed. Its core dependencies include `acorn`; SDK integrations have optional peers. `createCodeTool` wraps supplied capabilities for an AI SDK, whereas `createCodemodeRuntime` adds connector discovery, execution records, and approval operations. Both use an executor. The interface accepts code and host functions and returns a result, error, and logs. The package is not itself a self-contained secure Node executor. [Package README](https://github.com/cloudflare/agents/blob/455b47ec93f99f306f644ac06bc8b72b0627c1fc/packages/codemode/README.md).

[DynamicWorkerExecutor source](https://github.com/cloudflare/agents/blob/455b47ec93f99f306f644ac06bc8b72b0627c1fc/packages/codemode/src/executor.ts) uses a Workers `WorkerLoader` to execute JavaScript in a dynamic Worker. Namespaced proxies dispatch calls over Workers RPC to host-side functions. The executor defaults `globalOutbound` to `null` and a 60-second timeout in this revision. Those controls govern the Worker execution environment, not the authority of an RPC callback. A callback that can access credentials or a network still needs its own checks. Extra modules and bindings are explicitly configurable. The browser iframe executor is a different environment and its timeout cannot preempt a blocking synchronous loop.

The newer connector runtime changes an important detail in the first note. A connector marked `requiresApproval` causes an abort and durable pending record. Approval reruns the program and replays recorded results until it reaches the approved action. Its [runtime implementation](https://github.com/cloudflare/agents/blob/455b47ec93f99f306f644ac06bc8b72b0627c1fc/packages/codemode/src/runtime.ts) and [replay documentation](https://github.com/cloudflare/agents/blob/455b47ec93f99f306f644ac06bc8b72b0627c1fc/docs/codemode/runtime.md) show the limits: call order and arguments must match on replay, so concurrent `Promise.all` calls can diverge. A call recorded as executing when a crash occurs is treated as fresh on replay. An external effect may therefore repeat if it happened before the result was recorded. Rollback applies only where a connector supplies a working revert. Unawaited calls can continue on the host after the program returns. [Approval documentation](https://github.com/cloudflare/agents/blob/455b47ec93f99f306f644ac06bc8b72b0627c1fc/docs/codemode/approvals.md).

This is distinct from the older wrapper: [its resolver](https://github.com/cloudflare/agents/blob/455b47ec93f99f306f644ac06bc8b72b0627c1fc/packages/codemode/src/resolve.ts) filters tools marked `needsApproval`, and its framework-independent resolver does not validate input schemas. Do not infer either durable approval or validation merely from use of the package. A host must select and verify the relevant path.

**Self-hosting inference:** Cloudflare's Workers architecture is a useful design reference, but adopting the package does not transplant Cloudflare's hosted security boundary into Staf. [Local Workers development](https://developers.cloudflare.com/workers/local-development/) uses Miniflare and `workerd`, and warns that Miniflare is not a hardened sandbox. The [open-source workerd project](https://github.com/cloudflare/workerd) supports self-hosted Workers but explicitly requires an additional secure sandbox for possibly malicious code. A local integration would need to establish Worker Loader and RPC support, a suitable process or VM boundary, deployment, updates, and the Durable Object storage dependencies of the connector runtime. Local development support is not evidence that this complete production arrangement is ready for Staf. No local integration or license compatibility review was performed.

## Local runtime shortlist

All candidates need an explicit host bridge, resource and output limits, process supervision, and an evaluation of the actual release on Staf's platforms. None makes a privileged callback safe.

- **QuickJS compiled to WebAssembly.** [quickjs-emscripten at `7b7af98`](https://github.com/justjake/quickjs-emscripten/blob/7b7af98e4e69757c64c27aac46a74e1e07229545/README.md) provides JavaScript contexts, host functions, memory limits, and an interrupt handler. Host promises can become guest promises, but the host must pump pending jobs or deadlock. Its Asyncify variant can suspend for an asynchronous host operation, but only one suspension per WASM module at a time. An approval wait, simultaneous child calls, cancellation, and worker termination thus need explicit design and tests. The project says it has not had a security audit. A separate constrained process is a candidate for defense in depth, not a proven Staf sandbox.
- **Monty from Node.** [`@pydantic/monty` at `96c609c`](https://github.com/pydantic/monty/blob/96c609c8571bf876e985eaf449a9c3d2adf78290/crates/monty-js/package.json) declares version 1.4.0, MIT, Node 20 or later, and native platform packages. The [Node binding](https://github.com/pydantic/monty/blob/96c609c8571bf876e985eaf449a9c3d2adf78290/crates/monty-js/README.md) runs **Python**, not JavaScript, in subprocess workers. Its separate WASM entry uses worker threads. The [binding's native source](https://github.com/pydantic/monty/blob/96c609c8571bf876e985eaf449a9c3d2adf78290/crates/monty-js/src/pool.rs) describes turn-level suspension and a TypeScript host loop for callbacks and futures. [Snapshots](https://github.com/pydantic/monty/blob/96c609c8571bf876e985eaf449a9c3d2adf78290/docs/snapshots.md) can pause at a host call and later resume, a possible approval mechanism if Staf protects snapshot integrity and compatibility. Monty's [security documentation](https://github.com/pydantic/monty/blob/96c609c8571bf876e985eaf449a9c3d2adf78290/docs/security.md) says execution-time limits pause during host calls, local request timeout defaults to no deadline, and sessions must be discarded after time or memory limits. The host must bound wall time, suspensions, and callbacks separately. Cancelling a worker does not prove a dispatched host effect was cancelled. Python subset differences and whether selected models use it reliably remain open.
- **V8 isolates.** [isolated-vm at `d180c55`](https://github.com/laverdet/isolated-vm/blob/d180c5539e2d889d6e1048256b162156af6b1ad2/README.md) exposes Node/V8 isolates and asynchronous references, but is in maintenance mode. Its maintainer recommends a separate process, warns that leaked references can expose the host, and says its memory limit is not a strict ceiling. Async callback timing and termination require particular scrutiny. This is a lower-priority candidate, not an endorsed security boundary.

A separately constrained container or VM with a minimal message bridge remains another option, but adds host dependencies and operations. `node:vm` is not a candidate security boundary: [Node explicitly says](https://nodejs.org/api/vm.html) it is not a security mechanism. A sandbox may also run out of memory or have implementation defects even when host capabilities are restricted.

## Providers and the model-facing contract

A portable route is an ordinary provider function tool with an input schema containing a code string. The provider returns the call; Staf validates it and executes the code locally. [OpenAI's function-calling guide](https://developers.openai.com/api/docs/guides/function-calling) documents JSON-schema function tools and separately documents free-form custom tools. Support for the latter is provider-specific and not necessary for the code-string route. [OpenRouter](https://openrouter.ai/docs/guides/features/tool-calling) and [LM Studio](https://lmstudio.ai/docs/developer/openai-compat/tools) also document client-executed function calls for supported models. API support does not establish that a particular Staf provider, model, authentication path, or adapter will generate correct and safe programs. Check each rather than extrapolating from the protocol.

Provider-managed programmatic calling is a different execution and data boundary. [Anthropic's documentation](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling) runs generated code in its container and returns calls to application-defined tools to the application. Its current constraints include text-only programmatic child results, no `strict: true` programmatic tools, and no programmatic calls to MCP connector or computer and browser toolsets. This does not imply the same limits on a local Staf bridge or ordinary direct calls. Container lifetime, supported model, data handling, and adapter behavior must be evaluated separately.

One model-facing `exec` does not eliminate capability definitions. The service still needs stable names, descriptions, input and output schemas, error shapes, side-effect classifications, and discoverable limits. It validates each invocation and result at the trusted boundary. Discovery may start with a compact index and expose detailed schemas on demand; it must return enough information for the model to choose and handle errors. [MCP's tools specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) illustrates optional structured output schemas and content blocks, but Staf need not adopt MCP to define its internal contract.

Represent structured data and multimodal content explicitly. A script's JSON result, text, binary artifact reference, image, and error are not interchangeable. Preserve provenance, MIME type, size, and access scope when passing an artifact to a model or client, and use provider-specific encoding only at the adapter. A text-only route must report unsupported content or provide an authorized reference; it must not silently describe an image as if the model saw it. Validate real provider support before promising multimodal results.

## Authority, state, and failure

Staf should own credentials, conversation history, capability dispatch, permission and scope checks, approval grants, and the action journal outside the executor. For every child call, validate arguments and authorize the actual action, including after an approval wait. A script approval alone is not authority for every future action. Associate child calls with their parent invocation, preserve actual outcomes, and present concise work in the chat message list. Bound input, output, child-call count, concurrency, CPU, memory, wall time, and per-capability use.

Start an experiment with fresh, disposable state per invocation. Do not confuse script variables or a serialized interpreter with conversation history or retained memory. If durable waits or state are later required, specify ownership, versioning, expiry, cleanup, and trusted snapshot integrity. Approvals may outlive a worker or the service process, so define whether to suspend, replay, or terminate and ask the model to continue. Each strategy needs a crash-recovery contract.

Stop must prevent new child dispatch and request cancellation of in-flight calls, but cannot promise rollback. Record completed, failed, and unknown effects distinctly. A restart must not silently rerun an uncertain write. Use stable action identities and operation-specific idempotency when available; otherwise reconcile with the external system before retry. Host limits must apply even while a guest waits for a human or a callback. Concurrent calls need explicit limits and a defined ordering policy, especially when approvals or replay are involved.

Treat returned pages, files, tool descriptions, and tool results as untrusted data. A malicious document can instruct the model to invoke an authorized action or cause a script to pass data to a capability. Isolation limits ambient access, but cannot decide the user's intent. Keep host authorization independent of model instructions, restrict destinations and data returned, avoid executing source text as code, and test injection attempts. These controls reduce risk; they cannot guarantee that the model interprets every document correctly.

## Falsifiable next experiment

This is a proposed future experiment, requiring separate implementation authorization. Before it starts, pin executor versions and platforms, agree on a fixed fixture corpus, scenarios, success criteria, and a record of every run. Compare a direct-tool baseline against code using the same service capabilities, tasks, permissions, fixture inputs, and observable child actions. Include simple clock-like requests, dependent search and read with filtering, a large result, malformed arguments, denied and approval-gated actions, a synthetic write with an idempotency key, concurrent calls, hostile content, cancellation, worker death, and restart after an uncertain effect. No real credentials or external effects are needed for these deterministic tests.

The proposed gates are:

1. **Boundary:** every denied or unapproved child is blocked, every actual child action is recorded, and neither guest code nor returned fixture text gains ambient filesystem, network, credentials, or an unapproved capability. Any bypass fails the gate.
2. **Recovery:** Stop prevents new dispatch, completed and uncertain effects remain distinguishable, and restart or approval never silently repeats a synthetic effect. Test the crash between effect and recording. Any duplicate or unreported uncertain effect fails the gate.
3. **Function:** both paths return the expected structured answers and preserve required text and artifact metadata. Record every failed case and repair attempt. Any lost required content or incorrect authorization fails the gate.
4. **Model fit:** in a separately authorized, model-backed evaluation across the actual target provider and model combinations, pre-register task set and thresholds for success, corrections, token use, latency, and cost. Compare simple and compound tasks independently. A scripted driver demonstrates bridge behavior only; it cannot prove code-writing reliability or provider compatibility.
5. **Operations:** demonstrate installation, bounded resource use, failure recovery, and updates on the supported native and Docker deployment paths. Record the complete added dependency and maintenance burden. An unverified isolation boundary or unsupported required platform blocks adoption.

Choose primary code mode only if all boundary and recovery gates pass, model results meet the pre-registered thresholds without a material simple-task regression, and the owner accepts the operational cost. Otherwise keep direct model tools, document the failed gate, and revisit with a specific change. No performance gain or model reliability is claimed here.

## Recommended path through the skills

This is a proposed sequence for future work. The research has not started these flows or created tickets.

1. **`/grill-with-docs` to settle the product boundary.** Take Code Mode as the leading target and settle which provider and model combinations must support it, local deployment requirements, what denying a child action means for the rest of a script, and whether execution state must survive an invocation. Preserve existing service ownership and owner-only controls. Record resolved terms and consequential decisions in the existing domain docs.
2. **`/architect with checkpoint` to choose the shape.** Compare two concrete designs for the local executor and host-call bridge. Sketch caller usage, capability and result types, approval waits, child identities, limits, and Stop or restart behavior. Name the runtime versions and supported platforms to evaluate. The explicit checkpoint keeps this step at a reviewable design before implementation.
3. **`/to-spec`, then `/to-tickets`, for the bounded experiment.** Publish the agreed experiment and its pass or fail gates to GitHub. Make the first ticket a complete path through one outer code call, a host capability, an approval decision, recorded child progress, and returned data. Follow it with failure and recovery coverage and a separately authorized model evaluation. Keep production migration blocked on the evidence.
4. **`/implement` for the experiment.** Use an isolated issue branch and PR, real local execution, synthetic effects, and the agreed checks. A browser simulation cannot establish isolation or callback cancellation. `/prototype` remains useful if approval or partial-result presentation needs an interactive exploration, but the execution question requires the actual candidate runtime. Record failed cases and dependencies as well as successes.
5. **Update the spec with the result, then use `/implement-spec` for adoption.** After the experiment passes, capture the chosen runtime and model support in the migration spec and ticket graph. Migrate capabilities through one shared contract, preserve deterministic client operations, and remove redundant model-facing direct tools as each supported path is replaced. `/implement-spec` integrates the ticket work and runs `/code-review` over the result. Leave the resulting PR open for review, with normal setup commands, manual checks, and clear offline versus live evidence.

The immediate next flow is `/grill-with-docs`. Its input is this research and the owner's preference for a streamlined primary Code Mode interface. A production executor choice remains an evidence-dependent decision.
